# Local Supabase via Docker Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up a local Dockerized Supabase stack that mirrors the remote project (`kvlvkjifhfvzvyeafgcx`), and let the `ocl` CLI flip between remote and local by adding/removing a `.env.local` file.

**Architecture:** Use the Supabase CLI (`npx supabase`) as a thin orchestration layer over `docker compose`. The CLI handles container lifecycle, migration sync (`db pull`), and data dumps (`db dump`). At the app layer, `src/supabaseClient.ts` loads `.env.local` first (when present) then `.env`, so the presence of `.env.local` switches the client to local creds without code changes. Remote stays the source of truth — local is a mirror, refreshed on demand.

**Tech Stack:** Supabase CLI, Docker Desktop, `@supabase/supabase-js`, `dotenv`, Node.js / tsx (existing).

---

## File Structure

| File | Action | Responsibility |
|---|---|---|
| `supabase/config.toml` | Create (via `supabase init`) | Local stack config (ports, JWT secret, etc.) |
| `supabase/migrations/*.sql` | Create (via `supabase db pull`) | Schema snapshot from remote — replayed on `supabase start` / `db reset` |
| `supabase/seed.sql` | Create (via `supabase db dump`) | Data snapshot from remote — auto-applied after migrations |
| `.env.local` | Create (manual) | Overrides for local Supabase URL + anon key. Absent = use remote. |
| `.gitignore` | Modify | Ignore `.env.local`, Supabase tmp files |
| `src/supabaseClient.ts` | Modify | Load `.env.local` first, then `.env` |
| `package.json` | Modify | Add `supabase` devDependency + `db:*` scripts |

Why this shape: the `supabase/` folder is the canonical home the CLI expects. `.env.local` is a well-understood Node convention for "machine-specific override of `.env`." The `dotenv` library does not override already-set variables, so loading `.env.local` *first* gives it priority over `.env`.

### Task 9: Wire app to prefer `.env.local` over `.env`

**Files:**
- Create: `.env.local`
- Modify: `src/supabaseClient.ts`

- [ ] **Step 1: Create `.env.local` with the values from Task 7**

Create a new file `.env.local` at the repo root with the values you copied from the `supabase start` output. The URL is always `http://127.0.0.1:54321` and the anon key is the long `eyJ...` JWT printed under `anon key`:

```
SUPABASE_URL=http://127.0.0.1:54321
SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOiJzdXBhYmFzZS1kZW1vIiwicm9sZSI6ImFub24iLCJleHAiOjE5ODM4MTI5OTZ9.<rest-of-key>
```

Note: the local anon key is a static, well-known JWT signed with a default secret (you can see it in `supabase/config.toml` under `[auth] jwt_secret` if you ever change it). It is NOT a real credential and is safe to type wrong — `supabase start` will reprint it any time.

- [ ] **Step 2: Replace `src/supabaseClient.ts`**

Current contents (8 lines):

```typescript
import 'dotenv/config'
import { createClient } from '@supabase/supabase-js'

const supabaseUrl = process.env.SUPABASE_URL!
const supabaseKey = process.env.SUPABASE_ANON_KEY!

export const supabase = createClient(supabaseUrl, supabaseKey)
```

Replace with:

```typescript
import dotenv from 'dotenv'
import { createClient } from '@supabase/supabase-js'

dotenv.config({ path: '.env.local' })
dotenv.config({ path: '.env' })

const supabaseUrl = process.env.SUPABASE_URL!
const supabaseKey = process.env.SUPABASE_ANON_KEY!

if (process.env.SUPABASE_URL?.includes('127.0.0.1') || process.env.SUPABASE_URL?.includes('localhost')) {
    console.log('[supabase] using local stack')
}

export const supabase = createClient(supabaseUrl, supabaseKey)
```

Why two `dotenv.config` calls: `dotenv` does **not** override variables that are already set in the environment. So loading `.env.local` first wins; `.env` then fills in anything `.env.local` didn't define.

The console.log is a soft indicator so you know at a glance whether you're hitting the local or remote stack — easy to remove later.

## Operational Notes (post-implementation)

- **Refreshing local from remote:** `npm run db:pull && npm run db:dump && npm run db:reset`. This re-syncs schema, dumps fresh data, and re-applies both to local.
- **Switching to remote temporarily:** rename `.env.local` to `.env.local.disabled` (the rename trick from Task 11 Step 3). Rename it back to switch to local.
- **Docker disk usage:** the `supabase_db_<project_id>` volume grows with your data. `npm run db:stop` does NOT delete it. To fully reset, `npx supabase stop --no-backup` then `npx supabase start`.
- **JWT secret:** the local anon key in Task 9 is signed with a publicly-known default secret. Do NOT expose `http://127.0.0.1:54321` to the open internet — it's a dev tool.
